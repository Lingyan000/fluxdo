# FluxDO 文档

`docs/` 只放以后还会有人回来查的长期参考。一份文档如果只在写它的那次任务里有用，就不该入库。

## 能入库的

- **入口文档**：开发环境、发版、打包等操作说明，从 README 或 AGENTS.md 链接过来。
- **设计依据**：代码注释里写了 `设计依据: docs/<文件>.md §<章节>` 的文档，例如 Cookie 架构。
- **长期契约**：接入规则、协议流程、不变量，以及新代码必须遵守的约定，例如后台 WebView 的租约规则、分片上传协议、平行视界接入约定。
- **不看文档就容易改错的原因**：为什么选这个方案、为什么不能用看似更简单的做法、平台或 SDK 的坑。例如 Release 包里 `--impeller-backend` 不生效，Android 视频改走平台视图的原因。
- **与 Discourse 上游的对应**：官方前端或服务端的实现位置（带 commit 或链接），以及客户端怎么适配。

## 不能入库的

| 内容 | 放到哪里 |
| --- | --- |
| 会话过程：「本轮」「接续记录」「检查点」、测试通过了多少项、APK 哈希、CI 运行号 | 提交信息正文或 PR 描述 |
| 一次性诊断输出、抓包、日志分析、netlog | 留在本地，或贴进 PR / issue |
| 方案草稿、实施计划、成本评估 | 留在本地，定案后把结论写进代码注释或契约文档 |
| 从代码直接能读出来的参数表、文件清单 | 不写，读代码 |

已经实施的计划、已经被新文档取代的旧方案，要么改写成现状，要么删除。git 历史里能找回，不用为了留档保留过时的文档。

## 写法

- **写现状，不写过程**：描述系统现在是什么样、为什么这样，不写「本次修改了」「之前的结论有误」。确实需要记录历史时，单独放一节「演进」，并且只写对理解现状有用的部分。
- **不写日期和轮次**：标题和章节名描述功能本身，不写「2026-11-05 第二轮」「续查」。只有版本号本身有含义时才写（如 Cookie 架构 v0.4.0）。
- **写清边界**：哪些情况已经覆盖，哪些不保证。只写结论，不罗列测试用例。
- **从问题出发**：文档回答的是「我们的问题该怎么解」。围绕现象、约束、可选方案和取舍展开，结论由项目自己的数据、协议、平台行为和实测推出。依据是 Discourse 上游、平台文档或开源库源码时，附上链接或 commit。不以某款产品的做法作为方案的依据，也不写成和某款产品逐项对照的报告。
- **文件名**：kebab-case 英文，不带日期，例如 `shared-webview-runtime.md`。
- 中文书写，代码标识符用反引号。

## 新增前

1. `ls docs/`，先看有没有同主题的文档，有就更新它，不要另开一份。
2. 想清楚以后谁会在什么时候读它。答不上来，就放进提交信息或 PR。
3. 文档描述的是代码约定时，在对应代码的注释里写上文档路径（和章节），这样改代码的人能找到它。

## 改名与删除

被代码或其他文档引用的文档，改名或删除前先查引用，然后同步更新：

```sh
git grep -n "<文件名>" -- ':!assets'
```

引用通常出现在代码注释（`设计依据: docs/...`）、README、AGENTS.md、vendor 目录的 `UPSTREAM.txt`。删掉被引用的文档前，先确认引用处是否还依赖其中的内容。如果依赖，保留它，或者先把需要的内容并入引用方。
