Android OCSP 提供者兼容修复（2026-11-16，Asia/Shanghai）

问题
- 0.2.29 不使用当前 Core 的 Java 补充撤销检查；统一 Core 后，系统信任已通过的连接
  仍可能因默认 PKIX 提供者不实现 getRevocationChecker() 而被拒绝。
- 前次提交仅解决未携带 staple 的情形。携带合法 OCSP 仍被拒绝是剩余兼容性退化，
  不能把“接口未实现”解释为“证书无效”。也不能由此直接确认 issue #433 的实际根因。

修复
- 平台仍先验证主机名、证书期限、用途和信任链。
- 无 staple 时沿用前次兼容逻辑；有 staple 且检查器不支持时使用本地验证。
- 不使用 Android 隐藏 API，不添加根证书，不通过联网访问证书中地址完成兜底。
- ASN.1 使用已有 yasna/x509-parser；签名与摘要使用已有 BoringSSL，无新增依赖。
- 比对当前叶子的序列号、签发者名称/公钥摘要；签发者只取平台构建的可信链。
- 支持签发 CA 直接签署和具有 OCSPSigning 授权的直接委托响应者。
  后者必须由当前 CA 签发、证书有效且允许数字签名；响应自带证书不会被直接信任。
- 验证响应签名及算法参数、producedAt/thisUpdate/nextUpdate；时间偏差容忍 5 分钟。
  无 nextUpdate 的响应最多接受 7 天，防止无限重放。存在 nextUpdate 时按其期限检查。
- revoked、unknown、关键扩展不可识别、签名/身份/编码错误均拒绝；同一证书多状态按严格结果处理。
- 响应大小上限 256 KiB，最多 64 条状态和 16 张响应者证书；错误不回显证书或网络地址。
- Java 提供者的其他异常仍拒绝。已有检查器的路径以及 iOS/macOS/Windows/Linux 平台信任策略未改。

验证
- OpenSSL 独立生成响应，且对主要正向响应再次独立验签，未使用校验豁免。
- 29 组响应对照：CA/委托响应者、byName/byKey、SHA-1/SHA-256 CertID、RSA/ECDSA/RSA-PSS，
  以及 revoked、unknown、错误签名/序列号/签发者摘要/响应者、同名其他 CA、缺少授权/证书、
  过期响应者、错误 KeyUsage、关键扩展、RSA-PSS 盐长度/MGF/尾字段、错误状态、尾随数据和截断。
- 另测响应过期、未来时间、无 nextUpdate 的旧响应，以及逐字节截断/翻转时不 panic。
- 真实 JVM 调用生产 JNI 能力探测和本地桥接，同样覆盖正常、可选接口不支持与 SecurityException。
- 用已有 Android 15 android-all 系统类运行真实 BC 提供者，确认抛出不支持异常后本地验证仍正确工作。
  这是 Android 实现代码在宿主 JVM 上的验证，不是 Android 真机或 Wi-Fi/蜂窝网络实测。
- 临时测试私钥不进入仓库、不安装到系统；未消耗 BrowserStack 设备额度。

复现入口
- cargo test --locked --lib ocsp_tests -- --test-threads=1
- FLUXDO_ANDROID_ALL=/path/to/android-all-15.jar cargo test --locked --lib android_revocation_tests -- --nocapture
- 完整 Core 回归及架构守卫、各平台编译沿用现有 Network regression CI，不增加诊断工作流。
