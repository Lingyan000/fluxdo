范围
- 原生 WKWebView 与生产 Core 各自发送九种合成请求：原有七种请求，加上同一条件值第二次、第三次使用。
- 使用相同请求顺序、连接阶段和字段值；比较实际共同字段的 QPACK 表示，不复制业务 Cookie、Origin、Referer 或 CSRF。
- macOS 与 iOS 模拟器分别测试原生 UA、应用 UA；Core 均在 macOS 执行，不等同 iOS 本机 Core 或完整 Flutter 应用。
- 原生模式不传强制 QUIC/SPKI 参数，由 WKWebView 根据 Alt-Svc 选择协议。回环证书仍使用诊断宿主的限定端口证书回调。

诊断修复
- 扩展原生采集与生产 H3 校准采用一致的切换步骤：先公告 Alt-Svc，响应写出后关闭旧 TCP 连接；只在尚未进入场景的 GET 就绪轮询中容忍切换异常。
- iOS 每次启动分配独立结果文件；宿主原子写入，驱动读取并验证，控制台原文保留在 stderr。文件缺失或宿主失败仍判失败。
- 比对器还要求 Core 完整采样、原生驱动成功；输出区分原生 Alt-Svc 和 Chromium 强制 QUIC 条件。
- 本地 Chromium 156 七场景回归通过，13 项既有比对器检查与 8 项架构守卫通过；缺失采样、失败驱动及结果文件缺失的负对照均被拒。

已确认的生产问题
- Actions 43723394118（macOS 两组）和 43724258592（macOS、iOS 15.5 各两组）均收齐七个目标 H3 请求，值与正文一致，但共同字段编码不一致。
  原生稳定请求使用 DynamicIndex，Core 仍使用 DynamicPostBaseIndex；新路径、条件值、Range 值被 Core 过早插入动态表。
- 三次重复 fetch 只覆盖了 Apple 的启动阶段，第三次仍是 post-Base；把这一阶段永久用作稳定策略不成立。
- Actions 43724853464 加入同条件值第二、第三次使用。两组 macOS 都实际发出 LiteralStaticName → DynamicPostBaseIndex → DynamicIndex。
  说明新值第一次字面量、重复后入表，不能把所有 Automatic 字段立即插入，也不能简单禁止动态编码。
- 43723394118 的 iOS 26.2 两次预热均超时，未进入网络测试，不计入编码结论。

生产修复
- 同一路径至少采三阶段，并要求最后两次字段策略一致；最多七阶段。不稳定时不启用 H3。
- 每个独立 origin 再用一个新路径的首次、重复访问测量入表规则；不支持、无效、敏感或缺少的样本拒绝发布。两组 origin 的规则须一致。
- 复用准入模式按当前连接中的实际字段值处理，首次字面量，重复时入表；Base 使用本字段块开始时的表边界，后续按当前表索引编码。
- 字段记忆有动态表容量和字段块预算双重限制，跳过敏感字段；连接重建从空状态开始。未增加平台或版本白名单。
- CSRF 业务逻辑和值、Cookie/Origin/Referer 业务策略未改。
