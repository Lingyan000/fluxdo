QPACK 多请求场景（2026-11-15）

后续 Apple 扩展验证发现并修复启动阶段误用和新字段值过早入表，详见 h3-apple-qpack-20261115.txt。
原七场景现补充同一条件值第二、第三次使用，共九场景；下文保留首轮 Chromium 验证的历史范围。

已确认并修复
- FromFieldPreferences 的 Base 规划原先把 Automatic 字段直接选成静态/字面量，跳过动态表。
  Chromium 156 同流序号对照显示 If-None-Match、Range、变化后的 If-None-Match 均不一致。
  修复为精确静态命中仍保留，其余自动字段使用本连接当前值规划动态表。
  不复制捕获的动态索引；敏感标记、表容量、阻塞预算和插入失败回退继续生效。
- 普通 fetch 的 Accept-Encoding 模板不适用于 Range：Chromium 99/110/156 实际均发 identity。
  Range 现在保留显式 Accept-Encoding，未指定才补 identity；普通请求仍沿用原模板策略。
  该处理共享于 HTTP/1.1、H2、H3。Range、条件值和 CSRF 不被修改。
- 比对器同时核验 Accept-Encoding 的值，避免不同值都使用 DynamicIndex 时被误判通过。

验证
- QPACK 组件 118 项通过，包含新增自动字段首次插入、复用、值变化、敏感字段不插入；已有零容量回退用例通过。
- Range 单元测试覆盖三个 HTTP 版本和缺省/identity/gzip 三种调用方编码。
- Chromium 99.0.4812.0、110.0.5481.38、156.0.8078.79：七类顺序请求全部通过，共 21 组。
  场景：条件 GET、表单 POST、JSON POST、Range GET、HEAD、条件值变化、再次表单 POST。
  条件：本机强制 QUIC + 实验 SPKI，浏览器与 Core 均在新 fetch 连接上先完成三次请求。
  关闭导航连接，页面使用 data: 图标，避免 favicon 占用待比较连接的请求流。
  核验每请求只收到一次、流序号一致、同一连接、方法、正文 SHA-256、业务字段值、Accept-Encoding 值、共同字段 QPACK 表示。
- 使用真实通过产物作为正对照，篡改编码值、删除请求、重复请求、错误摘要、错误表示五类负对照全部被拒。

历史失败与边界
- 原生 Alt-Svc 但未强制 QUIC 的第一组发生实验 CA 校验失败，未计入回放通过。
- 第一组强制实验受 favicon 占用 stream 0 干扰，保留结果；同流序号的后续对照才用于确认编码问题。
- 新工具只比较实际发送的共同字段，另列 source_fields_not_requested；不声称整个请求头集合、顺序或原始 QPACK 字节完全相同。
  例如浏览器 POST 的 content-length 并非当前 Core 每次都会发出；不能把 21 组共同字段通过说成完整浏览器指纹一致。
- 仍未验证导航、图片/媒体资源等所有请求用途，以及每个平台的所有动态表状态；不将 Chromium 结果外推为 Safari 或真机结果。
- CSRF 业务逻辑和字段值未改。BrowserStack 新增设备会话为 0。
