H3 Initial 布局续查（2026-11-15）

已证实的问题
1. Chromium 156 的原生首包携带 ClientHello 头部及尾部，中段在后续包；旧 Core 只能包内乱序。
2. 旧 Core 最小分片 32 字节、额外 PING 上限 3，与 Chromium 99/110/156 的实测及源码不符。
3. iOS 26.2 的真实模拟器 WKWebView 样本按 999 字节切 CRYPTO；旧 Core 按 1161 字节。
   两者 UDP 包大小仍相等，所以此前仅比较 datagram_sizes 的报告漏掉了这一差异。
   证据：Actions 43702919972 / artifact 14157540394，tool/testdata/ios26_initial_layout.json 保留原始元数据。
4. 采集端在响应发送完成后才记录请求，客户端退出时可能丢失最后一条观测。
   同时 warm 请求头先于其 PRIORITY_UPDATE 到达，会使控制帧集合偶发缺项。

实现
- 实测首包有 CRYPTO 中段空洞时，按当前握手长度重新规划首包头尾及后续中段，再做包内细分。
- 多包有序样本从数据推导分片上限；两次校准要求该特征一致，不把 999 写成平台常量。
- 初始布局只存偏移、长度、帧形状；真正发送使用新 TLS 数据，普通 ACK/丢包恢复队列继续跟踪 CRYPTO。
- 现有预算限制、token、CID、包头保护长度、拥塞窗口等完整检查仍保留。
  不适配的布局由底层回退，不声称所有握手长度与所有网络事件都维持同样指纹。
- 旧单包与观察到跨包交错的策略采用各自有源码依据的随机范围。
- 采样等待已观察到的逐请求 PRIORITY，2 秒内未到则明确失败；不影响普通业务请求。
- 请求在响应前记录；比对器新增 CRYPTO 完整无重复覆盖、跨包策略、有序分片上限检查。

范围限制
两条连接的随机样本不能证明完整分布，短 ClientHello 的现代单包路径与历史单包策略仍可能歧义。
本轮未推断所有 Chromium 分支/实验开关的切换版本；不能把结构检查通过称为全指纹等价。
iOS/macOS 的修复已用下述新云端抓包复核；真机、WiFi/蜂窝切换、生产 CF 结果仍另行验证。
QPACK 全部请求用途矩阵、Android/Windows 默认原生 H3 证书信任、真机网络场景仍不因本补丁完成。
CSRF 业务逻辑和字段值未修改；本轮 BrowserStack 新会话数为 0。
