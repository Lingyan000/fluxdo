确定的新证据
- 四份 NetLog 各有 22 个本机 URL request source，22 次实际收到的 Alt-Svc 响应头。
- 每份证书验证都记录 cert_status=4、net_error=-202（ERR_CERT_AUTHORITY_INVALID）、
  is_issued_by_known_root=false；每份都有 21 次 SSL_HANDSHAKE_ERROR(-202)。
- 日志记录证书错误、调用证书回调、随后重新建立 TLS/H2 并读取响应。handler.proceed 允许
  继续访问，不等于将证书状态变成正常可信证书。
- 精确版本 Chromium 124.0.6367.219 的 http_network_transaction.cc:1334 明确要求
  SSLInfo 有效且 !IsCertStatusError(cert_status)，才调用 ProcessAlternativeServices。
  原始证书状态、收到 Alt-Svc 和版本源码共同说明当前本地自签证书路径不能正常学习该升级入口。
  这比前轮仅凭零 UDP 的推测更强；未声称抓到了源码分支执行的函数级追踪。
- 每份出现 43 个 type=dns_alpn_h3、using_quic=true 的 HTTP_STREAM_JOB，但没有本机
  QUIC_SESSION 观测，桥接器发送为零。创建 DNS ALPN 候选任务不能当作已进行 QUIC 握手。
- 当前直接阻碍发生在正常证书状态与 Alt-Svc 接纳条件；强制 QUIC 后的已知根限制是另一层，
  前轮 proof_verifier_chromium.cc 证据仍有效，不能把两层混为同一条已执行路径。

日志完整性边界
- Android NetLog 是应用仍存活时读取的流式前缀；旧分析器直接 json.loads 会报未封闭数组错误。
- 新分析器仅保留完整事件、要求常量区完整，明确输出 document_complete=false 与丢弃尾部字节数。
  不修改原始日志，不把未封闭前缀补成完整证据，不用缺少事件证明后续永远不会发生。
- 本轮四份分别保留 5539/5546/5550/5549 个完整事件，均没有半条事件残余字节，但外层文档未关闭。
  证书错误与 Alt-Svc 头是前缀中实际存在的正向证据；UDP 为零另有原生桥接计数及 Core 观测佐证。

跨平台已修复问题
- Core 在 TLS profile hash 改变时会清空 H3 模板，并增加内部 epoch，但旧状态接口不公开该值。
  Flutter 只用核心端口、UA、探针端口记忆是否尝试过；上述值未变时，重新校准被永久跳过。
- 现将 epoch 纳入状态接口，Flutter 用端口、UA、epoch、按探针顺序取出的 SPKI 共同标识尝试。
  核心新一代或证书变化会再采两个 origin；同一代失败仍只尝试一次，证书映射键顺序变化不重试。
- 两个新增 Flutter 回归在修复前明确失败（应有两轮探针，实际只有一轮），修复后通过。
  状态机、Windows 环境生命周期和架构守卫共 29 项通过，定向 Flutter 分析无问题。
  Rust H3 模板六项通过，包含 epoch 状态与 reset 一致性的断言。
- 此为 Android/iOS/macOS/Windows/Linux 共用状态协议修复，不添加平台或版本白名单。
  Windows 独立环境行为沿用前轮已验证实现，本轮没有再次消耗 Windows 云端构建。
- Android 命令行隔离十项与 NetLog 分析四项测试通过。

剩余边界与下一步条件
- 不能通过继续调用证书错误回调、增加等待时间或伪造 UA 修复默认 H3 采样入口。
  可信远程采样需要受控域名、浏览器信任的证书和可直接终止 QUIC/UDP 的服务。
  GitHub Pages 或普通 HTTP 反向代理不能提供服务端原始 QUIC/H3/QPACK 观测。
- Windows 独立 profile 与业务 profile 的持久化实验配置是否一致仍未证明。真实引擎、同版本、
  同 UA 和独立探针的报文对照通过，均不能替代业务 profile 本身的 H3 采样证据。
  本轮未复制业务 profile 或实验种子，也未以固定开关覆盖用户浏览器配置。
- 尚无已连接的上述可信入口及完整真机执行条件；Android 默认 H3、业务 profile 对齐、
  iOS 真机本机 Core、蜂窝切换与线上 CF 放行仍未闭环，PR 保留 Draft。
